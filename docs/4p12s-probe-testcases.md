## 二、统一测试输入（业务原始需求）

```
【业务原始需求】我们是 AI 网关团队，提供多个大模型代理服务。
现在运营反馈：告警系统用"单次首 token 延迟 > 3 秒"判断模型体验劣化，误报太多——
同一个模型有时 1 秒有时 5 秒，值班同学疲于奔命，已经出现狼来了效应。
我们要把判据改成统计口径：同一用例跑多次，看 P95 分位是否超阈值。
第一期先支持 P95，跑 5 次取最坏那个作为 P95 的近似；数据要能在测试报告里看到
（P95 数值 + 采样次数）。P99 和并发采样暂不做。验收：跑 qwen 内网模型时用例
显示 P95=xxx ms、N 次采样字样，且延迟稳定时不再误报。
```

## 四、链式执行规则

- 上一步产物整体作为下一步输入（②→③→④→⑤→⑥→⑦；⑧ 独立任务书；⑨⑩ 依赖⑧产物）
- 任一步失败即记录 attempts，**预算翻倍自动重试**（默认最多 2 次，对抗思考耗尽）
- 每步记录：耗时 / prompt tokens / completion tokens / 门禁结果 / attempts 次数
- 模型参数：max_tokens=6000（可调）、temperature=0.3

## 五、思考泄漏检测（v3 门禁）

代码注释行命中以下推理独白关键词即计数（`thinking_leak_lines` 指标）：

```
wait / let me / let's / hmm / i need to / 让我 / 等等 / 嗯
```

判例：Qwen3.8 曾在⑧步泄漏 70 行 "Wait, let's re-verify the math…" 独白为注释——pytest 过但 CR 必挂。泄漏行数 > 0 时报告中标黄，建议人工仲裁。

## 八、判定汇总口径

| 指标 | 含义 |
| --- | --- |
| steps_passed / steps_total | 过门禁步数（9 为满） |
| total_elapsed_s | 9 步总耗时（模型速度） |
| total_completion_tokens | 总产出 tokens（成本） |
| attempts > 1 的步数 | 需重试的步（稳定性） |
| thinking_leak_lines | 思考泄漏总行数（代码卫生，0 为佳） |
| ⑧⑨⑩ pytest_gate | 三道确定性执行门禁（必须全 True） |
