# nlaut 判定引擎架构白皮书
## —— LLM Judge 与 Agent-as-Judge 分工协作范式

**版本**：v0.4.0  
**日期**：2026-10-31  
**作者**：nlaut 框架核心团队

---

## 执行摘要

nlaut 框架提出了一种**分层判定架构**，将传统 LLM Judge 与新兴的 Agent-as-Judge 按场景分工，形成"确定性 → LLM → Agent"三级漏斗，在保证判定准确性的同时优化成本和延迟。

**核心发现**：
- **LLM Judge 无证据时假阳性率高达 22-33%**（消融实验：陷阱样本被放行 3-6 个）
- **Agent-as-Judge 假阳性率为 0%**（自主取证，客观验证）
- **成本权衡**：Agent 成本是 LLM Judge 的 5 倍，但避免了不合格模块进入生产环境的风险
- **最佳实践**：证据已打包时用 LLM Judge（快、省），证据需获取时用 Agent-as-Judge（准、安全）

---

## 一、背景：为什么需要两种 Judge？

### 1.1 传统 LLM Judge 的局限

传统 LLM-as-Judge 方法依赖**预先提供的 Evidence**进行判定：

```
被测系统自述：{"status": "任务已创建成功"}
提供的 Evidence：{"title": "任务已创建"}
LLM Judge 输出：PASS（基于文本推理）
```

**问题**：如果被测系统"表面说成功但实际未落库"，LLM Judge 会被欺骗：

```
真实情况：数据库中没有这条记录
LLM Judge 看到：{"status": "任务已创建成功"}
LLM Judge 判定：PASS（假阳性）
```

**风险量化**：在 20 个陷阱样本的消融实验中，LLM Judge（无证据）放行了 **3-6 个**不合格样本。

### 1.2 Agent-as-Judge 的突破

Agent-as-Judge 引入**自主取证能力**：

```
被测系统自述：{"status": "任务已创建成功"}
Agent-as-Judge 决策：
  1. "需要验证任务是否真实落库"
  2. 调用 read_file(path="~/.gienx/design-task.json")
  3. 解析 JSON，查找对应记录
  4. 有记录 → PASS，无记录 → FAIL
```

**优势**：不依赖被测系统的自述，而是通过工具获取**客观证据**。

**风险量化**：同样的 20 个陷阱样本，Agent-as-Judge **0 个假阳性**。

## 二、架构设计：三级判定漏斗

nlaut 采用**分层漏斗架构**，按证据可用性和判定复杂度路由：

```
┌─────────────────────────────────────────────────────────────────┐
│                     判定请求入口                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌──────────────┐                                              │
│   │ 1° 确定性判定 │ ← DOM 断言、响应断言、数值比较               │
│   └──────┬───────┘                                              │
│          │ 失败/不确定                                          │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 2° LLM Judge │ ← 证据已打包、文本推理、低成本快速判定        │
│   └──────┬───────┘                                              │
│          │ 需要更多证据                                         │
│          ↓                                                      │
│   ┌──────────────────┐                                          │
│   │ 3° Agent-as-Judge│ ← 自主取证、客观验证、高风险场景         │
│   └──────────────────┘                                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1 第一级：确定性判定

**适用场景**：
- DOM 元素可见性（`text_visible`）
- 属性值验证（`attribute`）
- API 响应结构验证（`response_json_schema`）
- 数值边界检查（`response_length`, `response_time`）

**特点**：
- 无 LLM 调用，零延迟（< 100ms）
- 100% 可重复，零抖动
- 成本：$0

**示例**：
```yaml
assertions:
  - kind: text_visible
    selector: '.task-title'
    expected: '测试任务-设计登录页面'
  - kind: attribute
    selector: '[data-main-view]'
    attribute: data-main-view
    expected: design-workbench
```

### 2.2 第二级：LLM Judge

**适用场景**：
- **证据已打包**：真值已经预先准备好，只需对比
- **文本语义判定**：回答是否切题、是否包含特定信息
- **低风险场景**：假阳性的后果可控

**特点**：
- 延迟：15-20 秒（含推理）
- 成本：$0.0005 - $0.001 / 次
- 假阳性率：10-22%（证据不足时）

**最佳实践**：**必须提供真值快照**

```yaml
assertions:
  - kind: visual_state
    prompt: "任务列表是否显示了刚创建的任务？"
    db_state:  # ← 关键：提供数据库快照
      tasks:
        - id: REQ-S31-15
          title: 测试任务-验证数据落库
```

**实验数据**：
| 证据状态 | 准确率 | 陷阱假阳性 | 翻转率 |
|---|---|---|---|
| 无证据（只有自述） | 68-73% | 3-6 个 | 40-45% |
| 有 db 快照 | 90% | 0 个 | 10-20% |

### 2.3 第三级：Agent-as-Judge

**适用场景**：
- **证据需动态获取**：无法预先打包真值
- **高风险场景**：假阳性会导致不合格模块进入生产
- **门禁验证**：G-11 "模块接入后数据是否真实落库"

**特点**：
- 延迟：15-30 秒（含工具调用）
- 成本：$0.002 - $0.003 / 次
- 假阳性率：**0%**
- 翻转率：**0%**（跨轮一致）

**工作流程**：
```
输入：被测系统自述 + 工具白名单 + 判定目标
  ↓
决策：模型决定调用哪些工具获取证据
  ↓
取证：read_file / query_db / http_probe / read_log
  ↓
对比：客观证据 vs 被测系统自述
  ↓
输出：基于证据的判定 + 置信度 + 取证轨迹
```

**实验数据**：
| 指标 | Agent-as-Judge | LLM Judge（无证据） |
|---|---|---|
| 准确率 | 100% | 68-73% |
| 陷阱假阳性 | 0 个 | 3-6 个 |
| 翻转率（跨轮一致性） | 0% | 40-45% |
| 中位延迟 | 15.5s | 22.8s |
| 单次成本 | $0.0025 | $0.0005 |

## 三、消融对照实验：Agent 的优势来自"自主取证"

### 3.1 实验设计

**控制变量**：同模型（deepseek-v4-flash）、同 rubric、同 20 个样本 × 3 轮 = 60 次判定

**自变量**：能否调用工具

| 组别 | 工具能力 | 证据来源 |
|---|---|---|
| Agent（实验组） | ✅ 可调用 read_file/query_db | 自主取证 |
| LLM Judge（对照组 1） | ❌ 无工具 | 只有被测系统自述 |
| LLM Judge + db 快照（对照组 2） | ❌ 无工具 | 自述 + 数据库快照 |

### 3.2 实验结果

| 组别 | 准确率 | 陷阱准确率 | 陷阱假阳性 | 翻转率 |
|---|---|---|---|---|
| **Agent** | **100%** | **100%** | **0** | **0%** |
| LLM Judge（无证据） | 68-73% | 59-78% | 3-6 | 40-45% |
| LLM Judge + db 快照 | 90% | 100% | 0 | 10-20% |

### 3.3 关键发现

**发现 1：Agent 的优势来自"自主取证"，不是"模型更强"**
- 同模型、同 rubric，唯一差异是能否调工具
- 准确率差距 26-32 个百分点，全部归因于取证能力

**发现 2：LLM Judge 无证据时不稳定**
- 翻转率 40-45%：同一判定请求，两次结果不一致
- 假阳性 3-6 个：陷阱样本被放行

**发现 3：给 LLM Judge 喂 db 快照也能达到 100% 陷阱准确率**
- 但仍需预先准备好证据，无法应对动态场景

### 3.4 成本权衡

| 方案 | 单次成本 | 陷阱假阳性 | 适用场景 |
|---|---|---|---|
| LLM Judge（无证据） | $0.0005 | 3-6 个 | ❌ 不推荐 |
| LLM Judge + db 快照 | $0.0004 | 0 个 | ✅ 证据可预先打包 |
| **Agent-as-Judge** | $0.0025 | 0 个 | ✅ 证据需动态获取 |

**ROI 分析**：
- Agent 成本是 LLM Judge 的 **5 倍**
- 但避免了 **3-6 个假阳性** = 避免了 3-6 个不合格模块进入生产环境
- 单个不合格模块的修复成本 >> 5 倍判定成本差

## 四、应用场景：各司其职

### 4.1 LLM Judge 适用场景

| 场景 | 判定类型 | 证据来源 |
|---|---|---|
| API 响应验证 | 语义正确性 | 响应 body + schema |
| 大模型能力评测 | 回答质量 | 金标准答案 |
| 文档一致性检查 | 内容匹配 | 文档内容 vs 规范 |
| 低风险功能验证 | UI 文本/流程 | DOM 快照 |

**判定条件**：
1. ✅ 真值可以预先准备好（数据库快照、预期响应、金标准答案）
2. ✅ 假阳性的后果可控（非核心功能、可快速回退）
3. ✅ 判定逻辑主要是文本对比、语义匹配

**不适用**：
- ❌ "任务是否真实落库"（需要查库，证据无法预先打包）
- ❌ "文件是否真实创建"（需要查文件系统）
- ❌ "外部系统是否真实调用"（需要查日志/网络）

### 4.2 Agent-as-Judge 适用场景

| 场景 | 判定类型 | 取证工具 |
|---|---|---|
| **G-11 门禁**：模块接入后数据是否落库 | 数据持久化验证 | read_file / query_db |
| **G-12 门禁**：外部系统调用是否成功 | 集成验证 | http_probe / read_log |
| 数字分身 AI 行为正确性 | 输出落地验证 | query_db / inspect_trace |
| 不退化回归（G-13） | 历史数据对比 | read_file / query_db |
| 跨模块数据流验证 | 端到端链路追踪 | 多工具组合 |

**判定条件**：
1. ✅ 真值无法预先打包（需要实时查询）
2. ✅ 假阳性后果严重（不合格模块进入生产环境）
3. ✅ 判定逻辑需要查询文件/数据库/API/日志

**安全机制**：
- **工具白名单**：`allowed_path_roots` 限制可读取的目录
- **成本预算**：`max_cost_usd` 防止超支
- **超时熔断**：`per_call_timeout_s` 防止卡死
- **置信度封顶**：最高 0.85，强制走人工仲裁

## 五、最佳实践：判定引擎选择指南

### 5.1 决策树

```
判定请求
    ↓
┌───┴───────────────────────────────────┐
│ 真值能否预先打包？                      │
└───┬───YES → LLM Judge + db 快照        │
    │        （快、省、准）               │
    │                                    │
    NO ↓                                 │
┌───┴───────────────────────────────────┐
│ 假阳性后果严重吗？                      │
└───┬───NO → LLM Judge（无证据）         │
    │        （接受 10-20% 误差）         │
    │                                    │
    YES ↓                                 │
┌────────────────────────────────────────┐
│ Agent-as-Judge                         │
│ （自主取证、0 假阳性、5 倍成本）        │
└────────────────────────────────────────┘
```

### 5.2 配置示例

**LLM Judge 配置**（证据已打包）：
```yaml
# 测试用例 IR
assertions:
  - kind: visual_state
    prompt: "任务列表是否显示了刚创建的任务？"
    # 提供 db_state，让 LLM Judge 可以对比
    db_state:
      tasks:
        - id: REQ-S31-15
          title: 测试任务-验证数据落库
          status: not-started
```

**Agent-as-Judge 配置**（自主取证）：
```yaml
# 测试用例 IR
assertions:
  - kind: agent_verify
    prompt: |
      验证设计任务"测试任务-验证数据落库"是否真实落库。
      1. 调用 read_file 读取 ~/.gienx/design-task.json
      2. 查找 title 包含"验证数据落库"的记录
      3. 有记录则 pass，无记录则 fail
    truth_sources:
      design_tasks:
        type: file
        path: ~/.gienx/design-task.json
    max_cost_usd: 0.10
    max_steps: 4
```

### 5.3 性能调优

| 参数 | 默认值 | 调优建议 |
|---|---|---|
| `max_steps` | 4 | 复杂判定提高到 6，简单判定保持 2 |
| `max_cost_usd` | 0.50 | 门禁场景 0.10 足够，探索性测试提高到 1.00 |
| `per_call_timeout_s` | 45 | 网络不稳定时提高到 60 |
| `temperature` | 0.0 | 判定场景保持 0，探索性可提高到 0.3 |
| `confidence_threshold` | 0.85 | 不建议修改，强制走人工仲裁 |

## 六、技术实现：TruthSource 契约

### 6.1 真值源抽象

Agent-as-Judge 通过 `TruthSource` 协议访问真值：

```python
class TruthSource(Protocol):
    def query(self, table: str, columns: list[str], where: dict) -> list[dict]:
        """查询指定表的行"""
        ...

    def locate(self, table: str, keyword: str) -> list[dict]:
        """按关键词定位记录"""
        ...
```

### 6.2 四种实现

| 实现 | 数据源 | 初始化方式 |
|---|---|---|
| `DictTruthSource` | 内存字典 | `TruthSource({"task": [{...}]})` |
| `HttpTruthSource` | HTTP API | `TruthSource(url, headers)` |
| `SqlTruthSource` | SQL 数据库 | `TruthSource(connection_string)` |
| `LogTruthSource` | 日志文件 | `TruthSource(file_path)` |

### 6.3 接入示例（设计任务文件）

```python
# 配置 truth_source_registry.yaml
design_tasks:
  type: file
  path: ~/.gienx/design-task.json
  description: 设计任务文件，包含所有设计任务记录

# 在测试用例中引用
truth_sources:
  design_tasks:
    type: file
    path: ~/.gienx/design-task.json
```

## 八、结论与建议

### 8.1 核心结论

1. **LLM Judge 无证据时不可靠**：假阳性率 22-33%，翻转率 40-45%
2. **Agent-as-Judge 是唯一跨轮稳定的方案**：0% 假阳性，0% 翻转率
3. **成本权衡清晰**：Agent 成本是 LLM Judge 的 5 倍，但避免了不合格模块进入生产
4. **最佳实践**：证据可打包时用 LLM Judge，证据需获取时用 Agent-as-Judge

### 8.2 实施建议

**短期（P0）**：
- 为高风险门禁（G-11、G-12、G-13）部署 Agent-as-Judge
- 为 LLM Judge 补充 db_state 参数，将准确率从 70% 提升到 90%

**中期（P1）**：
- 建立判定引擎自动路由机制（根据证据可用性自动选择引擎）
- 扩展 TruthSource 实现，接入日志系统、APM 平台

**长期（P2）**：
- 建立 Agent-as-Judge 模型池（支持多模型、多端点）
- 开发判定结果可视化面板（取证轨迹、成本分析、置信度分布）
